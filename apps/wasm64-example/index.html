Linux wasm64 embedding example

This example uses a real Linux kernel and native wasm64 BusyBox. Each start creates a fresh in-memory ext4 disk. Stopping or reloading loses changes; this example does not save to OPFS.

Minimal BusyBox root (64 MiB); Python is not installed.

Serve on localhost or HTTPS with COOP/COEP headers. Browser support for shared memory and memory64 is required. This is not a security boundary between programs running inside the same Linux instance.

Run your own Linux wasm64 program

Select a static executable built with the matching Linux wasm64 SDK, not WASI, wasm32, or a native ELF binary (at most 16 MiB). The file is copied only into this temporary Linux disk, not uploaded to the server. Only run programs you trust: they can access or damage this Linux instance and its files.

The optional Python profile also accepts ZIP-format .pyz applications without a prepended shebang. Select Python explicitly; no format guessing or automatic dependency installation is performed. Python runs inside Linux with its installed standard library, not as WASI.

Standard input receives the selected source followed by EOF. File mode streams exact bytes without uploading to the server or loading the whole input into JS memory, and ignores the text field. Text mode ignores the file selection. Large files can take time; use Cancel application or Stop Linux if needed. Recent output is limited to 65,536 characters; stdout/stderr interleaving is not deterministic. Stop Linux remains available while an application runs; it stops the whole instance and discards the temporary disk, unlike cancelling one application.
